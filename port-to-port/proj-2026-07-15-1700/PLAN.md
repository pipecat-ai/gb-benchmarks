# Plan: Benchmark thinkingmachines/inkling on Baseten (port-to-port) + leaderboard

Project directory: `./proj-2026-07-15-1700`

## Context
Run the port-to-port natural benchmark against `thinkingmachines/inkling` on Baseten and add it to the leaderboard. The harness is already fully Baseten-integrated (prior effort `proj-2026-06-30-0924`, committed), so this is a focused add. **The one real integration risk:** the harness's Baseten branch sends effort as **nested** `extra_body.reasoning.effort` (which GLM reads — its 400 said "reasoning.effort must be one of…"), but the Inkling doc says Inkling honors the **top-level** `reasoning_effort` field. If those differ our mapping would silently leave Inkling at default effort — so a probe must PROVE the controlling field before we wire it.

## Rules
### Gating & compatibility
- Every Inkling behavior change is gated on `_is_baseten_inkling_model(model)` (exact normalized set `{"inkling","thinkingmachines/inkling"}`, NOT a broad substring) AND `_is_baseten_endpoint(openai_base_url)`. GLM, Nemotron, other Baseten models, and all non-Baseten providers must be byte-for-byte unaffected — assert with negative tests (including a non-Baseten "inkling"-named case).
- Do NOT edit installed pipecat. Reuse existing helpers/wrappers. Do NOT add a model gate to the 429 wrapper (it already covers Inkling by endpoint).
- The effort-control field/representation is decided by step-1 EVIDENCE with a stated threshold; inconclusive evidence BLOCKS step 2. Send exactly one control; remove competing stale controls (nested `reasoning`, native `reasoning_effort`, `chat_template_kwargs.reasoning_effort`) in the Inkling branch. Note: `1172-1173` unconditionally strips `chat_template_kwargs` — only change that for Inkling if the template field wins.
### Correctness (verify at the request boundary, not by inspection)
- `temperature=1.0`, `max_tokens=16384`, and the chosen effort control must appear in the FINAL `chat.completions.create` kwargs. Verify with an offline test that spies on `chat.completions.create` (or asserts `build_chat_completion_params`) — `inference_inputs[].provider_invocation_params` holds context messages/tools, not generation settings, so it cannot prove this.
### Data integrity & ops
- **Preserve every raw run JSON and log** — a failed run with JSON is benchmark data and must be judged, never deleted (`../AGENTS.md`). **Exact infrastructure classifier** (an attempt is infra-failed, hence non-canonical, iff): `summary.terminal_reason ∈ {rate_limit_exhausted, inference_error}` (the harness's Baseten API-error/exhausted-429 terminal reasons — note `inference_error`, NOT `inference_failure`), OR the worker exited 124 (PER_RUN_TIMEOUT) with no run JSON produced. Everything else (including genuine model `no_tool_call_stall`/`max_turns_exhausted`) is a real model outcome and IS canonical-eligible. **Canonical eligibility additionally REQUIRES a valid run JSON** — any attempt that produced no run JSON (regardless of exit code) is non-canonical and must be rerun (`../AGENTS.md:502`). **Canonical set = the first 25 canonical-eligible attempts per config by monotonically-assigned attempt number.** Reruns for infra/no-JSON failures go under a NEW attempt stem/run-dir; record counts. Cap infra/no-JSON reruns at **≤10 per config**, then stop and report (no unbounded retry/spend). Do not silently reuse a `RUN_DIR` across a config change (`round_is_done` only checks the success bool, not model/thinking/max_tokens).
- All Inkling runs strictly sequential (one episode per process) per `../AGENTS.md`; 429s handled by the existing wrapper. `PER_RUN_TIMEOUT` sized for `mt=16384` (step-1 timing).
- Do not overwrite committed leaderboards without user approval; generate scratch outputs and diff first; never mutate raw run artifacts in place. House-style naming uses **derivative copies** (renamed `model`→`inkling`). Path-join order (the builder joins run→enriched by resolved file path): create derivative copies of ALL new Inkling run JSONs FIRST, **judge those derivatives** (satisfies the repo "judge everything with JSON" rule AND makes enriched `file` paths match the leaderboard inputs), then symlink only the **canonical 25** derivatives per config into the leaderboard input glob. Combine the new Inkling enriched rows with the existing canonical enriched without rejudging any other model.
- `none` (folded-CoT) is **probe/smoke-only, never canonical** — the folded chain-of-thought makes its `content` non-comparable for the tool-use leaderboard. It is not in the full-run CONFIG_FILTER or expected count.
- Paired review (direct + cx-delegate, run by the orchestrator) after each step; each step independently committable; the orchestrator commits.
