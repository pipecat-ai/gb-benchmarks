# Plan: Benchmark GPT-5.6 (luna / sol / terra) on port-to-port

Project directory: `./proj-2026-07-16-1632`

## Context
Add the three OpenAI GPT-5.6 reasoning models (`gpt-5.6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`) to the port-to-port natural leaderboard. Because the benchmark always sends tools, these models **must** run on the OpenAI **Responses API** with `reasoning: {effort}` (chat-completions `reasoning_effort` 400s with tools). The harness already runs `gpt-5.4` this way; the work is to extend that path, gated to the exact GPT-5.6 set, with the same probe→harness→sweep→run→leaderboard arc + paired reviews as the Inkling effort. `gpt-5.5` is **probe-only** in this plan (a GO/DEFER verdict + evidence); its full benchmarking is a separate follow-up if GO.

**July 17 course correction:** the first production attempt exposed that the
new provider-output/encrypted-reasoning matcher was an unnecessary bespoke
layer. `../aiewf-eval` already runs GPT-5.6 robustly by reconstructing
Responses continuations from standard assistant function calls and function
outputs. The matcher and its v6-v9 validation ladder are retired. Engineering
fixes and offline validation proceed without incremental approval; only a
genuine expansion of the agreed live budget or scope is an approval boundary.

## Reference implementations
- **Official OpenAI docs (authority):** the GPT-5.6 model guidance documents `gpt-5.6-{luna,sol,terra}`, recommends the Responses API for reasoning/tool/multi-turn work, and defines the supported effort set as `none/low/medium/high/xhigh/max`; the model pages provide the current token prices and 128K maximum output. The GPT-5.5 model page documents Responses, function calling, and `none/low/medium/high/xhigh`. The Responses streaming reference defines `response.completed`, `response.failed`, and `response.incomplete` (with `incomplete_details`). The Priority Processing guide says priority should not be used for evaluations, so this benchmark **omits `service_tier`** unless a standard-tier request is proven unusable and the user separately approves an exception. Record the exact URLs and retrieval date in step 1.
- **aiewf-eval (service implementation):** `../aiewf-eval/src/multi_turn_eval/services/openai_responses.py` and `pipelines/base.py` are the application-level reference for Responses request construction, standard assistant/tool history reconstruction, function-call streaming, and GPT-5.6 effort routing. Port only that contract plus this benchmark's observability/timeouts; do not copy Pipecat 1.3 internals into the pinned 0.0.102 environment and do not add provider-output retention.
- **Local precedent (gpt-5.4):** `llm_factory.py:66-68` `_is_openai_responses_model` (routes `gpt-5.4*` iff `openai_base_url is None`); `mini-rl-env.py:1185-1188` gpt-5.4 thinking branch (`extra["reasoning"]={"effort": …}`, `none→none/minimal→low/else passthrough`, no `service_tier`). We mirror this. Step 1 verifies standard-tier usability and the `max` wire contract; any exception to the no-`service_tier` rule requires separate approval.
- **Inkling effort (`proj-2026-07-15-1700/`):** the structure/rigor to mirror — probe-gates the risk, exact-set gating, offline request-boundary spy, non-destructive scratch-diff leaderboard, canonical manifest + infra classifier, approval gate.

## Rules

### Decisions that MUST be locked in step 1 (before any harness edit)
1. **Docs baseline + live contract table:** record the official supported effort sets, Responses/function-calling support, prices, and maximum output; then use the bounded live matrix in step 1 only to verify this account's model access, Responses+tools round-trip, serialized `reasoning.effort`, returned event shapes, and standard-tier behavior. `service_tier` is omitted. Select a **provisional** `max_output_tokens` candidate here; the full-episode smoke in step 4 is what locks the production cap.
2. **The `max` mechanism.** gpt-5.6 exposes `max` above `xhigh`, but the benchmark's top `--thinking` is `xhigh`. Resolve concretely: add an explicit **`--reasoning-effort <level>` override** (or a config field) so a config can request `max` directly, and record the **effective effort** in the run JSON + leaderboard identity. This lets `xhigh` and `max` be **distinct** configs. (Do NOT silently map `xhigh→max` and lose native `xhigh`.)
3. **thinking→effort map**, avoiding duplicate API configs (`minimal→low` collides with `low→low`; do not spend rounds on both unless replication is explicitly wanted).
4. **gpt-5.5 verdict** — one of `GO_RESPONSES / GO_CHAT / DEFER_TRANSIENT / DEFER_UNSUPPORTED`, with evidence. gpt-5.5 harness/sweep/leaderboard work is OUT OF SCOPE of this plan (follow-up); `gpt-5.5-pro` is out of scope.
5. **Probe ceiling before any live call:** state the token/$/wall ceilings derived from official prices, obtain approval, and enforce them with a per-call output cap/wall timeout plus a conservative preflight reservation for the next request's bounded input, maximum output, and wall time. Never launch a request without that headroom. The live matrix is at most **24 API requests total**: 16 planned requests (seven two-call tool round-trips: GPT-5.6 `low`+`max` per version and GPT-5.5 `medium`, plus one GPT-5.6 and one GPT-5.5 chat+tools contract check) and at most 8 explicitly classified cap-escalation/transient retries. No repetitions for statistical sampling and no Priority requests.

### Model gating (exactness + endpoint)
- Gate on **exact normalized model equality** to `{gpt-5.6-luna, gpt-5.6-sol, gpt-5.6-terra}` (NOT `startswith` — `gpt-5.6-lunatic`/snapshots/aliases must NOT match) **AND** the same endpoint condition the router uses (`openai_base_url is None`). Share ONE full decision helper across routing (`_is_openai_responses_model`), thinking-mode, and validation so they cannot diverge. The gpt-5.6 thinking branch precedes the `gpt-5` catch-all. Non-interference is proven by **behavior-snapshot** tests (endpoint class, `extra`, max-token mapping, policy string) for gpt-5.4/5.2/5.1/gpt-4.1, custom-base-url, and non-OpenAI providers — not merely "files unchanged".

### API correctness (the key risk)
- gpt-5.6 uses the **Responses API** (`reasoning:{effort}`), never chat `reasoning_effort`. Because the service back-converts a stray `reasoning_effort`, the boundary test must (a) assert the **pre-service** `extra` contains `reasoning={"effort":…}` and `store=false` with no top-level `reasoning_effort`, AND (b) use an **HTTP-transport spy** that FAILS if `/v1/chat/completions` is hit and inspects the serialized `/v1/responses` body for `reasoning.effort`, `store=false`, tools, and `max_output_tokens`, driving the real param builder with captured step-1 success events (function-call argument deltas, completed, and usage). Exercise incomplete/failed paths with version-pinned, SDK-schema-validated synthetic event fixtures when those events were not observed live; do not spend live calls trying to manufacture provider failures. Pin + record the OpenAI SDK version.
- Multi-turn continuation uses only standard assistant `function_call` items and
  `function_call_output` items in Pipecat history, matching aiewf-eval. Do not
  request `reasoning.encrypted_content`, retain provider output objects, or
  attempt to match provider response groups back to split assistant messages.
- `OpenAIResponsesLLMService` must treat `response.incomplete` and `response.failed` as explicit response outcomes, not silent empty turns. Persist a sanitized per-inference Responses trace in run JSON: API surface, response ID, resolved model, response status, returned service tier, incomplete/error code and reason, token usage (including reasoning/cached tokens), requested effective effort/max output, and booleans for tools/store. Do not persist headers, API keys, or duplicate raw prompts in this trace.

### Runs & data (cost-bounded; frontier models)
- **Hard budget + abort.** Before the full run, state and get approval for a token/$/wall-time ceiling; the run aborts automatically if exceeded. The **smoke is the go/no-go**. Sol is very slow (a single xhigh review call ran 441s / ~10.8k reasoning tokens) — a 50-turn sol-xhigh episode may run very long; size the sweep accordingly (reduced, step-1-justified level set; not all 6×3).
- **Timeouts/concurrency/retry:** add explicit SDK request and stream-idle timeout controls plus a shell-enforced per-episode wall timeout (beyond `--function-call-timeout-secs`, which only bounds tools). All three models share the hosted OpenAI endpoint, so **concurrency is exactly 1**. Interleave configs sequentially, cap infra/no-JSON replacements at 10 per config, and **halt on the second consecutive identical error signature** for a config pending review.
- **Determinism/no bias:** preassign the identical `round_id` set (`r01`…`r25`) across configs and record it in config, metadata, enriched rows, and the manifest. The synthetic task/world is deterministic and the API exposes no benchmark seed here, so do not claim a model seed that is not sent. Interleave configs rather than run one model to completion; canonical = the deterministic **first eligible** result per `(config, round_id)` by attempt number; never cherry-pick among successful reruns, never replace a model-failure-with-JSON.
- **Infra classifier:** before live execution, fault-injection tests on the GPT-5.6 Responses path must lock how 429, retryable 5xx, request timeout, stream-idle timeout, `response.failed`, `response.incomplete`, exit 124, and no-JSON map to terminal reasons and eligibility. Canonical-ineligible infra is `terminal_reason ∈ {rate_limit_exhausted, inference_error}` OR exit-124-no-JSON OR no-JSON; `response.incomplete` due the configured output cap is a real failed-with-JSON result unless the smoke rejects the cap before the full run. Preserve and judge every raw JSON/log. The canonical manifest records round IDs, attempt order, source+derivative paths, response statuses, terminal reasons, usage, effective effort, hashes, and selected/rejected reason.
- **Automatic full-run budget monitor:** after every sequential episode, atomically update cumulative input/cached/output/reasoning tokens, estimated dollars by version, and elapsed wall time from the manifest/run JSON. Before the next episode, reserve its conservative maximum input/output charge and wall timeout; do not start it unless that reservation fits below every approved ceiling and the maximum-attempt bound.
